# Velo V0.9 Production Hardening & Audit Report

This report documents the results of the hardening, stress-testing, and zero-CPU-decode audit of Velo v0.9's native LiveKit zero-copy GPU video track consumption pipeline.

---

## Hardening Classifications

* **VERIFIED**: Executed and validated successfully.
* **FAILED**: Executed and failed.
* **BLOCKED**: Could not be tested because of an external limitation.
* **UNTESTED**: Not attempted.

| **Phase 4: LiveKit Renegotiation** | **VERIFIED** | Successfully handled server-initiated SDP renegotiation when a publisher joined a room *after* Velo subscribed. SDP Answer was exchanged natively and frames decoded cleanly. |

| **Phase 6: Error Injection** | **VERIFIED** | Validated invalid SDPs, missing SDPs, redundant `close()` calls, calling `next()` after close, and instant connection aborts. All raised deterministic Python exceptions without Rust panics or deadlocks. |

## 3. Engineering Risks and Recommendations

### Remaining Engineering Risks
1. **Dynamic Resolution Upscaling**: While `maxwidth=1920` and `maxheight=1080` covers standard 1080p WebRTC streams, a transition to 4K stream resolution will trigger decoder reconfigure failure (Error 801).
2. **First-Frame Startup Latency**: In the middle of a streaming session, Velo must wait for the next publisher IDR keyframe (typically 2-3 seconds) to begin decoding. The client API should ideally have a non-blocking poll mechanism or track startup state.

### Next Phase Recommendations
1. **Adaptive VNVDEC Buffer Scaling**: Extend `maxwidth`/`maxheight` configuration limits dynamically or expose them as configuration parameters in Velo's Python constructor.
2. **Verify Prebuilt Wheel Installation**: Move to verifying packaging and installations to close the remaining gaps for the V0.9 release.
