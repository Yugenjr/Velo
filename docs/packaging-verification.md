# Velo V1.0 Packaging Verification Report

This document reports the findings of the **Packaging Assumption Verification** phase, verifying the dependencies, compatibility, and requirements for Velo's distribution.

---

## 1. PyNvVideoCodec Distribution Verification

We verified the official package metadata from PyPI (version `2.2.0` of `pynvvideocodec`):
* **Normal PyPI Install**: **VERIFIED**. `pip install pynvvideocodec` successfully resolves and installs the prebuilt wheel directly.
* **Supported Python Versions**: **VERIFIED** (`requires_python >= 3.8`). Compiles wheels for `cp38` up to `cp314`.
* **OS/Arch Support**: **VERIFIED**. Packages wheels for `win_amd64` (Windows x86_64) and `manylinux_2_28_x86_64` (Linux x86_64), along with `manylinux_2_28_aarch64` and `manylinux_2_34_aarch64` (ARM64).
* **Native Dependencies**: **VERIFIED**. Pip installs the wheel natively; it does not bundle CUDA runtime libraries or display driver files.
* **CUDA Toolkit requirement**: **VERIFIED**. The host does **not** require a local CUDA Toolkit (compiler/headers) installed to run or compile the Python package. The display driver (which provides `libcuda.so.1` or `nvcuda.dll`) is the only system dependency.
* **NVIDIA Driver/Runtime requirement**: **VERIFIED**. System display driver supporting CUDA is required to dynamically resolve host-level GPU calls.
* **Licensing**: **VERIFIED**. The package is explicitly licensed under the **MIT License**.

## 2. Python ABI3 Feasibility

We audited PyO3 APIs used in Velo's native Rust code:
* **Stable ABI Compatibility**: **VERIFIED**. The crate interacts with Python only via standard type bounds (`PyObject`, `PyTuple`, `PyDict`, `PyModule`, `PyResult`).
* **DLPack/Capsule check**: **VERIFIED**. The native Rust code has exactly zero references to `PyCapsule` or DLPack. The capsule returned to Python is actually generated by `PyNvVideoCodec`'s `DecodedFrame` which implements the standard `__dlpack__` protocol. Velo merely passes the Python object back.
* **Stable ABI tag**: **ARCHITECTURALLY PLAUSIBLE**. We can safely target `abi3-py38` without API incompatibilities.

## 6. Decoder 1080p Limit Finding

We audited the `maxwidth`/`maxheight` initialization parameters:
* **Limitation check**: **VERIFIED**. It is **not** a hard hardware or architectural limit. It is a configuration choice in Velo's Rust client calling `CreateDecoder` to pre-allocate surface dimensions.
* **Impact**: Dynamic resolution shifts (simulcast layers switching) exceeding these dimensions trigger decoder errors.
* **Resolution**: Can be raised to `3840` and `2160` (or parameterized in the python constructor) to allow dynamic scaling up to 4K.

## 7. Intended User Experience

For the V1.0 release, the user experience will be:
```bash
pip install velo
```
Transitive pip resolution will automatically install:
* `torch` (with bundled CUDA runtime libraries)
* `PyNvVideoCodec` (handling the hardware interface)
* `websockets`, `livekit-api`, `livekit-protocol`

The user can immediately run:
```python
import velo
stream = velo.connect_livekit(room_url, token)
```
No compilers, Rust, or CUDA SDK setup are needed on the user's host machine.

## 8. Unresolved Risks

1. **Host CUDA Version Mismatch**:
   * *Risk*: Host system GPU driver version being older than the CUDA toolkit version compiled inside the downloaded PyTorch wheels.
   * *Mitigation*: Rely on the strict runtime import validation inside Velo's `__init__.py`.
2. **Dynamic Simulcast Bounds**:
   * *Risk*: The SFU shifting track quality parameters beyond the decoder's max limits causing driver reconfiguration crashes.
   * *Mitigation*: Parameterize `max_width`/`max_height` in Velo's python constructor with safe defaults.
